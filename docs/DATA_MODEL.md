# Data model

One JSON document (`.data/lemma-db.json`) stands in for the production database. Its shape is deliberately the shape a Postgres schema would have, so the swap is a repository layer, not a rewrite. All business rules live in `src/lib/domain/` and are shared by the admin UI, the public site and the seed generator.

```
StaffUser ──┐
            ├─< Reservation >─ Guest
Apartment ──┤       │  │
            │       │  └─< ReservationEvent   (audit trail)
            │       ├─< Payment ─ PaymentProof
            │       └─< HousekeepingTask ─< HousekeepingNote
            └─< NotificationRecord
Settings (singleton)          cleaningState: Apartment → status
```

## Statuses

**Booking** — `inquiry → reserved → fully_paid → checked_in → checked_out`, with `cancelled` reachable from any pre-arrival state.
**Payment** — `unpaid → partially_paid → fully_paid`, plus `refunded`. Tracked separately from the booking status on purpose: a guest can be *reserved and partially paid*, or *checked out and still owing*.
**Verification** — `pending → verified | rejected`, on each individual receipt.
**Cleaning** — `needs_cleaning → in_progress → clean`, with `maintenance` as a side exit that also blocks the unit.

## Invariants the code enforces

1. **Confirmed stays hold nights; enquiries and cancellations do not.** Overlapping `reserved`/`fully_paid`/`checked_in` reservations on one apartment are refused with a `409` naming the clashing dates and the guest's own reference.
2. `checkOut` is the morning the guest vacates — it is **not a charged night** and does not block the next arrival's same-day check-in.
3. `nights = diff(checkIn, checkOut)` and `totalAmount = nights × nightlyRate − discount`, recomputed on every write. The client's arithmetic is never accepted.
4. A folio's paid figure sums **verified payments only**. Pending receipts are surfaced separately, so the balance a receptionist quotes is the balance the property has actually received.
5. A balance may never go negative; an over-payment is refused at the dialog and again at the route.
6. `outOfService` or a `maintenance` task blocks new bookings on that unit. Deactivating an apartment with future bookings is refused — the stays must be moved or cancelled first.
7. Cancelling requires the apartment to be free of any *other* confirmed stay on those dates before it releases inventory; refunds are recorded as `kind: refund` rows inside the cancellation, so money and reason stay together.
8. Housekeeping completion is a *human* action: a calendar cell turning green never marks a unit clean.
9. Every status change appends to `reservation.history[]` with actor, timestamp and note. Nothing is overwritten.
10. `updatedAt` moves with every mutation, and `createdBy` records the staff member who opened the booking — the audit trail is what makes the demo's permissions meaningful.

## Money

Whole Kwacha only: `roundKwacha()` and `formatKwacha()` render `K1,200` / `K48,500`, no decimals — Zambian practice for accommodation. Deposits default to `settings.booking.depositPercent` (50) of the stay total. Rounding is applied once, at the folio, never per line.

## Derivation vs storage

Stored: the guest's phone number, the rate at booking, a payment, a note.
Derived on read: occupancy, available/occupied/cleaning counts, dashboard metrics, guest lifetime value and outstanding balance, receipt numbers, apartment last-30-day performance, next free night, day-by-day calendar cells.

Anything a user could catch you out on is computed from the records — that is what makes the demo defensible in front of an owner.
